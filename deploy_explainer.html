Deploying work.flowers

Five surfaces, three of them by hand.
Now one paste.

The site is Notion content published by Bullet.so, styled and scripted from this repo. Getting a change live used to mean touching five places and retyping a commit SHA into two of them. Here is what replaced that, and what checks it.

Stop deploying across five surfaces from memory. Like an animal.

TL;DR

Merge. Run scripts/bullet-head.sh. Paste one block into Bullet’s head and publish. Run scripts/verify-live.py to prove it landed. The SHA is never typed by hand, and the verifier fails loudly when the live site does not match the repo.

The loop

Five steps. Two are yours, three are the tooling’s. Select one to see what actually happens.

You

Merge the PR

Nothing about the live site changes yet. jsDelivr serves files by commit SHA, so the moment the merge commit exists on GitHub, the new charm_style_sheet.css and bullet_bundle.js are fetchable — they are simply not referenced by any page.

Both scripts run git fetch origin themselves. Merging in the GitHub web UI and forgetting to fetch used to leave your local origin/main a commit behind — and both tools would then agree with each other on the wrong commit.
Tooling

Generate the paste

scripts/bullet-head.sh resolves origin/main to a full 40-character SHA, fills it into both jsDelivr pins in head.html, strips the template’s comments, and copies the result to your clipboard.

# after a merge
scripts/bullet-head.sh
# or against anything else
scripts/bullet-head.sh <ref|sha>

It refuses to pin a commit that is not on origin/main, because jsDelivr reads from GitHub — a local-only SHA produces a pin that 404s for every visitor. It also re-emits the JSON-LD with every non-ASCII character escaped as \uXXXX, so the block is pure ASCII.

That escaping is not fussiness. On 6 Sep 2026 two em dashes reached the live site as mojibake, having been decoded as the wrong charset somewhere between the clipboard and the Bullet form.
You

Paste into Bullet

Settings → Custom Code → Head, replacing everything already there. Paste straight from the clipboard — do not route it through another editor and do not copy it back out of Bullet to check it. That round trip is what corrupts it.

The block carries both jsDelivr pins, the font links, the chat-widget script, and the sitewide Organization JSON-LD. The JSON-LD stays literal markup rather than moving into the bundle, so it is server-rendered: injecting the site’s primary entity from JavaScript would make Google’s view of it depend on a render pass that is delayed and not guaranteed.

Never hand-edit this in the dashboard. Edit head.html, merge, and re-run the generator — otherwise the repo stops being the source of truth and you are back to mirrors that drift.
You

Publish from Bullet

Bullet serves a stored render, not a live one. Custom-code edits sit in the dashboard until a publish regenerates the pages and pushes them to the CDN. Skip this and the site is unchanged, however correct your paste was.

Same mechanic as stranded pages: a page removed from the Notion tree keeps serving its last render forever, because a republish can only walk pages it can still reach. See What Bullet will publish in the README.
Tooling

Verify

Reading the live page tells you a pin is present. It cannot tell you the pin is right — a stale or mistyped SHA looks identical in the HTML. So the load-bearing check is a hash comparison: fetch what jsDelivr actually serves for each pin and compare it byte for byte against the repo at the expected commit.

scripts/verify-live.py
→ 22 checks, non-zero exit with a checklist of what is wrong

Around that it checks the head paste is complete, that the JSON-LD deep-equals the repo’s, that no retired paste has come back, that the body ids the class shim keys off still exist, that the homepage still matches jtbd_widget.html, and that nobody has changed a Bullet theme setting.

What if I get it wrong?

Every one of these has happened, or nearly did. Pick one to see which check catches it.

Why

Why the SHA pins stay

Pinning to @main looks like the fix

It would remove the paste entirely. It is still wrong: jsDelivr serves a branch ref with max-age=604800, so returning visitors keep stale CSS for up to a week — and the purge API cannot clear a browser cache.

A SHA is immutable

Pinned paths serve max-age=31536000, immutable. Every visitor gets the right bytes the moment the pin moves, with no purge and no cache window. Typing the SHA was the problem — not pinning it.

Still by hand

Two surfaces cannot be deployed from this repo. Detecting drift is the achievable goal there, and the verifier does that.

jtbd_widget.html

Pasted into a Notion custom-code block on the homepage. It looks like a repo file, but nothing in the repo moves it. The verifier fails when the live homepage stops carrying all 15 prompts.

Bullet theme settings

Not code at all — the Appearance picker emits its own tags. The verifier diffs the served #bullet-theme block against bullet_theme_baseline.css and flags any change.
